# Windows: Task Scheduler

Register a task with a Once trigger under the same interactive Windows account as the receiving Codex app. This puts scheduling under the OS rather than the tool's child-process lifetime. Windows recipes here are documentation-based; validate on the target host before claiming end-to-end delivery.

## Prepare the action

Resolve the real executable with `Get-Command codex`, the thread ID, Codex home, working directory, due time, and a unique task name. Inspect whether Codex is a native `.exe` or a `.cmd`/`.ps1` wrapper. A task action does not run through an interactive shell and will not inherit custom shell environment variables.

For a native executable using the ordinary account environment, this is the basic shape (replace the path and thread ID; arbitrary messages require correct Windows argument quoting):

```powershell
$TaskName = 'CodexQueue-' + [guid]::NewGuid().ToString('N')
$StartAt = (Get-Date).AddMinutes(5)
$action = New-ScheduledTaskAction `
  -Execute 'C:\absolute\path\codex.exe' `
  -Argument 'queue --thread THREAD_ID --message "Notification test: reply with the current time."' `
  -WorkingDirectory 'C:\absolute\workspace'
$trigger = New-ScheduledTaskTrigger -Once -At $StartAt
$principal = New-ScheduledTaskPrincipal `
  -UserId ([System.Security.Principal.WindowsIdentity]::GetCurrent().Name) `
  -LogonType Interactive -RunLevel Limited
Register-ScheduledTask -TaskName $TaskName `
  -Action $action -Trigger $trigger -Principal $principal
```

Use the already-recorded due time instead of recomputing now+5 minutes after a long setup. Do not overwrite an existing task with `-Force` merely to avoid a name collision.

For custom `CODEX_HOME`, wrapper dependencies, and stdout/stderr logs, generate a small user-owned launcher and schedule its interpreter by absolute path. Store message/thread/home/path values in a serialized data file; load and pass them as arguments rather than inserting user text into executable source. Set `$env:CODEX_HOME` inside that launcher, capture output to an absolute log, and propagate the native `$LASTEXITCODE`. Check quoting behavior on the installed PowerShell version. Avoid batch `call` with arbitrary message text because reparsing and percent expansion can change it. For a `.cmd` installation, prefer locating its native Codex executable; otherwise explicitly validate the wrapper invocation with a harmless payload before use. Do not bypass PowerShell execution policy to run a generated launcher; select a permitted action or report the constraint.

## Concrete launcher for logs and custom home

When PowerShell 7 is already available, this launcher avoids command-string quoting for native Codex arguments. Save it as a task-specific `.ps1`, with a sibling `request.json` generated by a JSON serializer. The JSON fields are `executable`, `workingDirectory`, `codexHome`, `threadId`, `message`, `stdoutPath`, and `stderrPath`, all resolved explicitly. Keep the executable native; this example does not launch `.cmd` files. Do not install PowerShell merely for this recipe without authorization.

```powershell
$ErrorActionPreference = 'Stop'
try {
    $r = Get-Content -LiteralPath (Join-Path $PSScriptRoot 'request.json') -Raw | ConvertFrom-Json
    $si = [System.Diagnostics.ProcessStartInfo]::new()
    $si.FileName = $r.executable
    $si.WorkingDirectory = $r.workingDirectory
    $si.UseShellExecute = $false
    $si.RedirectStandardOutput = $true
    $si.RedirectStandardError = $true
    $si.Environment['CODEX_HOME'] = $r.codexHome
    foreach ($arg in @('queue', '--thread', $r.threadId, '--message', $r.message)) {
        $si.ArgumentList.Add([string]$arg)
    }
    $p = [System.Diagnostics.Process]::Start($si)
    $out = $p.StandardOutput.ReadToEndAsync()
    $err = $p.StandardError.ReadToEndAsync()
    $p.WaitForExit()
    [IO.File]::WriteAllText($r.stdoutPath, $out.GetAwaiter().GetResult())
    [IO.File]::WriteAllText($r.stderrPath, $err.GetAwaiter().GetResult())
    exit $p.ExitCode
} catch {
    [IO.File]::WriteAllText((Join-Path $PSScriptRoot 'launcher-error.log'), $_.ToString())
    exit 1
}
```

Point the task action at the resolved absolute `pwsh.exe`, with `-NoProfile -NonInteractive -File "C:\absolute\task\launcher.ps1"` as its arguments. The message never enters that command string. This .NET argument-list API requires PowerShell 7; do not paste it into Windows PowerShell 5.1. Validate the generated launcher under the host's execution policy using a harmless executable before scheduling live delivery. This is a reference example and has not been executed on the macOS authoring host.

## Verify, cancel, clean up

```powershell
Get-ScheduledTask -TaskName $TaskName | Format-List TaskName,State,TaskPath
Get-ScheduledTaskInfo -TaskName $TaskName | Format-List LastRunTime,NextRunTime,LastTaskResult,NumberOfMissedRuns
```

Check the registered action and trigger as well. `Ready` confirms a scheduled task, not a queued message. After execution, inspect the launcher log for the queued-item ID. `LastTaskResult=0` without a matching run time can describe a task that has not run yet.

For cancellation, first check whether the exact task still exists. If absent, report it as already removed. Otherwise disable future launches, stop a running instance if needed, and unregister this task only; distinguish expected already-completed state from permission or scheduler failures:

```powershell
Disable-ScheduledTask -TaskName $TaskName
Stop-ScheduledTask -TaskName $TaskName
Unregister-ScheduledTask -TaskName $TaskName -Confirm:$false
```

After normal completion, collect evidence and unregister; no stop is needed. Task Scheduler retains a Once task's definition until cleanup. Already-queued messages are not cancelled by deleting the OS task.

## Conditions

- Keep the user logged in and the receiving Codex thread loaded. A busy thread may consume the message after its current turn; do not skip delivery merely because it is busy.
- The basic recipe assumes the machine is awake. Task settings such as `WakeToRun`, `StartWhenAvailable`, and battery restrictions change behavior; configure them only as appropriate to the user's request. Do not promise wake-up without checking host power support and policy.
- Native Windows and WSL may use different homes, binaries, and app-server contexts. Target the environment containing the intended thread; do not assume a Windows task invoking WSL reaches a native Windows thread.
