# Docs Writer

読者が作業を完了するために必要な情報だけを、現在のコードと設定に基づいて日本語で書く。依頼に読者、対象範囲、前提が不足している場合は、作業に必要な範囲だけ確認する。

## 読者と対象文書を決める

- 書き始める前に、主読者、読む目的、知りたいことを具体化する。指定がなければ、文書の役割と現在のコードから判断する。
- 作成または更新するドキュメントは、ユーザーが依頼で明示したものに限る。異なる読者向けの情報が必要でも、指示されていないドキュメントを新規作成、分割、更新せず、依頼対象から除外する。
- 構成と内容は主読者の目的に必要な順に選び、読者の判断や作業に不要な事実は依頼対象から除外する。
- たとえば利用者向けREADMEでは、機能、導入方法、基本操作を優先し、利用者の導入や操作に関係しないCI設定やリリース作業は書かない。

## 作成と更新

- ドキュメントには「読み手の興味がある情報」だけを書く。余計なことは書かない。
- 古い情報を残さない。現在のコードと食い違う説明は、現状に合わせて置き換える。
- 変更の履歴や作業中の事情などの歴史的経緯は本文に持ち込まない。互換性、前提、制限など読者の判断に必要な情報だけ残す。
- `効く``強い`の活用形を使わない。性能、互換性、確実性などの主張は、確認できる具体的な条件・数値・引用元がある場合だけ書く。根拠がない測定値や評価は作らず、主張ごと削除する。
- `正本`は使わず、`SSoT`と書く。`上流`は使わず、別のリポジトリを指す場合は具体的なリポジトリ名を、一般的な参照元を指す場合は`アップストリーム`を使う。
- 手順には、読者に必要な実行場所、入力、期待する結果を含める。失敗時の確認方法は必要な場合だけ記載する。コード例は現行のインターフェースに合わせる。

## lint

上記ルールを遵守した上で、文章を書き終えたら、対象ファイルを明示して次を実行する。

```sh
bun <absolute-skill-path>/scripts/lint-docs.ts <file> [files...]
```

`<absolute-skill-path>` はこのスキルの絶対パスに置き換える。引数に glob は使わず、相対パスは呼び出し元のカレントディレクトリから解決する。lint の指摘は内容を確認して修正し、修正後に再実行する。コマンドを実行できない場合や結果を確認できない場合、lint 済みとは述べない。

キャッシュ、初回の依存関係取得、終了コードの意味は [references/textlint.md](references/textlint.md) を参照する。
