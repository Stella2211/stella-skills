# Docs Writer

読者が判断や作業を進めるために必要な情報を書く。
入力は依頼、対象文書、関連するコード・設定・実行結果。
成果物は、対象範囲内の更新済み文書と、確認できた検査結果・未確認事項。

## このスレッドでの使用登録

このSkillを現在の仕事に適用すると決めたときだけ、実行するエージェント自身が一度登録する。SKILL.mdの閲覧・レビュー・編集だけでは登録しない。
現在のスキル一覧にあるこのSKILL.mdのディレクトリを基準に`../../hooks/skill-usage.py`を解決し、絶対パスで実行する。

```sh
uv run --offline --no-project python "<plugin-root>/hooks/skill-usage.py" activate
```

`<plugin-root>`は解決した実際のプラグインルートへ置き換える。ネイティブシェルの`CODEX_THREAD_ID`を使い、親の登録を子へ委任したり、別スレッドのIDを代入したりしない。
登録は繰り返しても同じ状態になるが、毎ターンの確認やHook復元後の再登録は不要。用途を切り替える場合は同じコマンドの末尾を`deactivate`へ変更し、状態確認だけなら`status`を使う。
登録できない場合は一度報告し、現在読める本文で作業を続ける。登録のためだけに権限を広げない。Hookは登録済みの親スレッドだけへ本文を復元し、未登録時に全Skillを投入する代替処理は行わない。

## 対象と役割を決める

- 主読者、読む目的、対象範囲、文書の役割を確認する。資料や会話から判断できることは再質問しない。
- 更新対象には、現在の依頼で指定された文書と、継続中の作業で更新することが既に合意されている進捗・知見の保存先を含める。
- 適用中の作業指示が必要な進捗・知見文書の作成を求めている場合、その保存先を作業範囲内で選べる。明示的な「このファイルだけ」などの限定は優先する。
- 別の読者向け文書や無関係な文書を、関連しそうという理由だけで作成・分割・更新しない。
- 委任・直接編集・実行ツールは適用されるAGENTS.mdに従う。このSkill自体は新しい委任や承認の仕組みを要求しない。

## 文書の役割に合わせて更新する

| 役割 | 更新方法 |
|---|---|
| README・手順・リファレンス | 現在のインターフェースに合わせて置き換える。不要な開発経緯を本文へ持ち込まない |
| 現在の進捗・引き継ぎ | 同じ項目の現在状態を上書きし、旧状態と同居させない |
| 再利用する知見・判断根拠 | 結論、適用条件、根拠、次回の行動を残す。重要な見送り理由や反証を失わない |
| 実験・障害の履歴 | 当時の条件と観測を保持する。現在の実装に合わせて過去の事実を書き換えない |

進捗、知見、研究記録、引き継ぎを作成・更新する場合は、[references/knowledge-writing.md](references/knowledge-writing.md)を読む。
通常のREADMEや小さな文言修正では、必要がなければ読み込まない。

## 根拠と内容

- 現在の仕様は現在のコード・設定、実験事実は対応するログ・成果物、判断はその根拠と適用条件に基づいて書く。
- 観測した事実、解釈、仮説、採用した方針、未確認事項を区別する。
- 根拠のない測定値・性能・完了状態を作らない。必要な仮説は仮説として残し、事実へ格上げしない。
- 古い情報を現在の説明として残さない。失敗した実験や撤回した判断は、再利用に必要な理由を保持して履歴と区別する。
- 計画に書いた機能を実装済みとせず、実装済みの機能を実環境で検証済みとしない。
- 根拠の参照先は、読者が結論を確認できるファイル・節・ログ・成果物を選ぶ。人間向け本文へ証拠の全内容を複写しない。
- 限界の記載は、結論の適用範囲を示すために行う。未確認事項を自動的に追加作業へ変換しない。

## 構成と文章

- 結論と読者の次の行動が分かる順序にする。時系列で作業を説明することを既定にしない。
- 一つの情報の更新先を一つに定める。他の文書には、その役割と参照先を書く。
- 見出しには、読者が検索する対象、症状、機能、判断内容を使う。日時や作業IDだけの見出しにしない。
- コマンドには必要な実行場所、入力、期待する結果を記す。失敗時の説明は読者の作業に必要な範囲に絞る。
- `効く`、`強い`の活用形を使わない。評価は対象、条件、比較軸、具体的な変化で書く。
- `正本`は使わず`SSoT`と書く。`上流`は使わず、別リポジトリなら具体名、一般的な参照元なら`アップストリーム`と書く。
- 短い知見を大きなテンプレートへ膨らませない。空欄を埋めるための推測や不要な節を追加しない。

## 仕上げとlint

変更した範囲について、根拠との整合、古い現在状態の混在、重複、参照先、次の行動の分かりやすさを確認する。
lintは文章表現の検査であり、事実・実験・現在状態の正しさを保証するものではない。

まとまった文書更新の終了時に、変更対象を明示して実行する。

```sh
bun <absolute-skill-path>/scripts/lint-docs.ts <file> [files...]
```

`<absolute-skill-path>`はこのスキルの実際の絶対パスへ置き換える。
globを渡さず、相対パスは呼び出し元のカレントディレクトリを基準にする。
近接した小更新はまとめて検査し、進捗の一行を変えるたびに全ドキュメントを検査しない。

指摘は意味を確認して修正し、対象ファイルを再検査する。
コマンドを実行できない、または結果を確認できない場合は、lint済みとは述べない。
実行環境の問題を、文書内容の誤りや研究作業全体の失敗と混同しない。

実行環境、キャッシュ、終了コード、失敗時の扱いは[references/textlint.md](references/textlint.md)を参照する。
