# Long Task Execution

ユーザーが求める成果に必要な作業を選び、実行結果から次の判断へ進む。
大量の検証、長い実行時間、整った管理資料そのものを成果としない。

## このスレッドでの使用登録

このスキルを作業に適用すると決めたとき、実行するエージェント自身が一度だけ登録する。内容の閲覧・レビュー・編集だけでは登録しない。

```sh
uv run --offline --no-project python "<absolute-skill-path>/../../hooks/skill-usage.py" activate
```

`<absolute-skill-path>`は現在のスキル一覧が示す、このSKILL.mdのあるディレクトリに置き換える。同梱helperは自分の`CODEX_THREAD_ID`を使う。親の登録を子へ委任したり、別スレッドのIDで上書きしたりしない。
登録済みなら再登録や定期確認は不要。確認は`status`、不要になった場合の解除は`deactivate`を同じコマンドの末尾へ指定する。通常の返答終了や会話の再開では解除しない。
Hookから本文が復元された場合は登録・同じ本文の読み取りを繰り返さない。子だけの使用登録は親へ合流しない。
登録エラーは簡潔に報告し、成功と称さない。IDや書き込み権限が不足しても推測・権限回避をせず、作業自体は続ける。その場合、自動復元には依存せず必要時にスキルを読み直す。

## 入力と成果物

入力は、ユーザーの目的、今回の依頼範囲、既存の計画・知見・成果物、利用可能な環境、許可された資源と操作。

維持する文書は次の二つ。プロジェクトが指定する保存先を優先する。

- 現行計画：目的、現在状態、作業一覧、実行中ジョブ、次の判断を記載する。
- 知見ファイル：このタスクで判明した結論を、適用条件・根拠・次回の行動とともに再利用可能な形で記載する。

進捗と知見は別ファイルにする。既存の適切な文書があれば再利用し、同じ役割の文書を増やさない。
保存先が未指定なら、対象作業の範囲内で`<TASK>_ACTION_PLAN.md`と`<TASK>_FINDINGS.md`等の分かる名前を選び、相互にリンクする。
実際に得られていない知見を埋め草として作らない。

依頼が計画・レビューだけの場合は、その成果物までを扱い、実行の許可と混同しない。

## 1. 今回の目標を定める

プロジェクト全体の長期目標と、今回依頼された成果物・完了条件を区別する。
必要な品質、判断したいこと、許可範囲、重要な制約を短く確認する。

既存資料と会話で解決できる点は調べる。
欠けている情報が重要な判断や許可を妨げる場合だけ質問し、独立して進められる作業は続ける。
計画作成のために、最初からすべての不確実性を解消しようとしない。

## 2. 現行計画を整える

同じ目的の計画があれば更新し、新規セッションやコンパクションを理由に作り直さない。
冒頭には次を置く。

- 今回の目標と完了条件。
- 現在の進捗を、作業IDを使った一文。
- 次の行動または判断と、実際のブロッカー。
- 実行中ジョブがある場合、その確認先と出力先。
- 知見ファイルへのリンクと最終更新日時。

作業表は工程単位で作る。
作業ID、実施条件、目的、必要な結果・完了条件、状態を記す。
判断に必要な場合は見積もりと見直し時点、明示的な上限も記す。
目的と最終目標との関係が同じ説明になる場合、列を重複させない。

状態は「未完了・進行中・完了」を基本とする。
待機・失敗・ブロッカーの詳細は説明欄へ置き、未確認の成果を完了にしない。
不要になった作業は現行計画から外し、理由を知見または履歴に残す。実施したことにはしない。

## 3. 次の作業と検証を選ぶ

作業を追加する前に、次のいずれかを具体的に説明できるか確認する。

- 依頼された成果を直接作る。
- 次の重要な判断を変え得る。
- 結果の無効化、重大な損失、不可逆な誤操作を防ぐ。

自分で追加した受入条件の存在だけを、追加作業の理由にしない。
現在の成果に不要な改善は必須工程へ入れない。

実験では、判別したい疑問、結果に応じた次の行動、検証を増やさず終える条件を先に決める。
少ない比較で次の判断ができるなら、予定した全候補・全入力を機械的に実行しない。
差が曖昧で、その差が次の選択を左右する場合に追加する。

技術的な動作確認、改善可能性の探索、完成成果物の品質評価を区別する。
単一の短期実験を長期的な性能保証に使わず、未確認範囲をすべて追加実験へ変換しない。

検証量は時間だけでなく、失敗時の損失、可逆性、費用、判断への影響に合わせる。
ユーザーレベルAGENTS.mdの検証・ハッシュ・ゲート方針を適用し、このSkillのために新しい承認基盤を作らない。

## 4. 委任して実行を進める

委任とモデル選択はAGENTS.mdに従う。
子には必要な資料、成功済みの実行経路、変更可能な範囲、求める成果までを渡す。

通常の実装修正は同じ工程内で完結させる。
importやパスの修正ごとに新しい作業IDを作り、親の再承認待ちへ変換しない。
目的、比較条件、予算、依存関係が変わる場合は現行計画を更新する。

独立作業は並行化し、同じGPU・メモリ・編集箇所などを競合させない。
親は各操作を指揮するより、次の判断に必要な成果が得られたかを確認する。

失敗時は、原因と残っている証拠を調べ、適用範囲内で修正・再試行する。
根拠のない同一試行を繰り返さず、成功済みの成果物を再利用する。
管理用の形式が不足している場合も、実行結果を既存のログや成果物から確認できるかを先に考える。

## 5. 時間と長時間ジョブを扱う

時間には三つの意味がある。

- 想定時間：現時点の見積もり。実測と区別する。
- 見直し時点：超過したら進展、原因、残作業、次の行動を確認する時点。
- 厳守する上限：ユーザーの許可、予算、資源制約、明示的な実験条件に基づく制限。

見積もりや見直し時点を、自動的にプロセスの強制終了条件へ変換しない。
明示された上限を勝手に延長しない。
未測定の工程へ見せかけの精密な見積もりを付けず、重要な見積もりの変更は報告する。

長時間ジョブには、既存の分離実行・保存・失敗検出・通知の仕組みを優先する。
実行前に、必要な入力・設定、初期進行の確認方法、失敗時の扱い、終了と成果物の確認方法を決める。
指定stepでの停止・保存・切替が必要なら、ジョブ側で実行されることを確認する。

起動しただけで正常進行とせず、最初の有効な処理が進んだことを確認する。
監視の仕組みが必要な範囲を満たしたら再利用し、毎回別のcontrollerやobserverを作らない。
待機・更新頻度はAGENTS.mdに従う。

## 6. 知見を別ファイルへ残す

このタスクで得た、今後の判断や作業に再利用できる知見を知見ファイルへ記録する。
完了時だけにまとめず、原因の特定、方針決定、仮説の棄却、重要な制約の発見などの節目で更新する。

記載するのは、結論、成立する条件、根拠への参照、次回の行動。
必要な場合は、未確認範囲と見直す条件も残す。
観測、解釈、仮説、採用判断を混同しない。

実行ログの貼り付け、SHA・PID・承認履歴の一覧だけを知見としない。
同じ知見が既にある場合は統合し、古い結論が現在も有効に見える重複を残さない。
過去の実験事実は履歴に保持し、現在の結論との関係を示す。

文書を書く担当は、利用可能なら`docs-writer`を適用する。
知見・進捗・引き継ぎを扱う場合は、その`references/knowledge-writing.md`も参照する。
利用できなくても、この節に従って必要な記録を残す。

## 7. 更新と再開

現在状態は、主要な成果、判断変更、ブロッカー、引き継ぎの時点で上書き更新する。
同じ作業IDについて複数の「現在」を残さない。
詳細な試行履歴は既存ログや履歴文書へ置き、現行計画へ時系列で積み上げない。

同じ文書の同じ範囲を複数の担当が同時に更新しない。
親は判断を確定し、担当が保存する。親の直接編集はAGENTS.mdの範囲内で行う。

コンパクション後は、このSkillの現行本文、現行計画、関連する知見を確認する。
Hookが全文を再投入した場合は重複読み取りせず、その内容を適用する。
実行中ジョブや未完了操作があれば必要な状態だけを確認し、検証済みの地点から続ける。

古い会話要約や旧計画を理由に、目的を変えたり、完了した調査をやり直したりしない。
矛盾は関係する箇所だけ調べて解消し、現在の文書を更新する。

## 完了の扱い

今回の完了条件を満たす成果物と必要な証拠を確認する。
未完了、失敗、未検証は区別し、作業量や推定進捗率で代用しない。

最終報告には、成果、採用した判断、重要な限界、現行計画と知見の保存先を示す。
許可された残作業があり実行可能なら、計画や続行の申し出だけで終了しない。
本当に外部入力や許可待ちなら、その依存関係と再開地点を明示する。
